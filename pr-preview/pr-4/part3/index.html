Partie 3 | Projet

Objectifs

À l’issue de cette partie, chaque étudiant.e sera capable de :

  • Appliquer une méthodologie de développement à un projet réel, en équipe

  • Produire les documents associés (cahier des charges, fiche technique)

  • Développer un logiciel fonctionnel et le documenter

  • Analyser et présenter, de façon critique, le déroulé du projet à la lumière de la méthodologie suivie

Le fil rouge : le préliminaire

Un TP préliminaire sert de fil rouge à tout le cours :

Un client veut un logiciel de vente de produits (cosmétique, fruits, menuiserie, art, films, musique, …) avec un système de recommandation pour les utilisateurs.

Consigne : développer le logiciel en documentant chaque étape (documenter vos choix, basés sur vos connaissances du moment). Livrables : un petit rapport (10 pages max) + une petite démo. Le préliminaire n’est pas noté (sauf s’il n’est pas rendu) : il alimente ensuite les exposés, le TP1, le TP2 et le projet.

1. Les exposés (20 %)

Chaque groupe présente en profondeur une méthodologie assignée par l’enseignant (Cascade, V, Itératif, Spirale, Agile/Scrum, Agile/Kanban) — typiquement un exposé par séance, sur ~2h.

Contenu attendu :

  • Une description de la méthode ;

  • Le plus important : utiliser l’exemple préliminaire comme base pour expliquer l’exécution pas-à-pas de la méthode ;

  • Les cas d’utilisation : avantages, limites, contextes d’application.

3. TP2 — Fiche technique (20 %)

En groupe, produisez la fiche technique du préliminaire (voir chapitre 3) : architecture générale (MVC, design patterns, API/REST), diagrammes UML (cas d’utilisation, classe, objet, séquence), choix logiciels, maquettes, gestion des données.

Rappel

La fiche technique doit permettre de réaliser le logiciel sans recontacter le client ni relire le cahier des charges.

4. Le projet (40 %)

Le projet se déroule en équipe, chaque groupe se voyant assigner une méthodologie (V, Itératif, Spirale, Agile/Scrum, …). L’objectif : développer une plateforme à la lumière de la méthode assignée.

Attendus :

  • Décrire chaque étape du développement ;

  • Analyser les forces et faiblesses de la méthodologie suivie ;

  • Présenter les cas d’utilisation (grand/moyen/petit projet : e-commerce, logiciel, mobile, …) ;

  • Présenter la solution ;

  • Analyser le résultat obtenu à la lumière des défis de la méthode utilisée.

Selon la méthodologie assignée, le suivi diffère. Par exemple en Agile/Scrum, l’enseignant joue le rôle du client et vous le rencontrez à la fin de chaque sprint.

Livrables :

  • Un rapport en anglais (~10 pages) ;

  • Le code ;

  • Un document de déploiement et d’exécution (README) ;

  • Une vidéo (5 min max : démonstration d’utilisation + « pub »).

Note

Variante hackathon (selon l’année). Certaines années, le projet prend la forme d’un hackathon : un seul projet pour toute la promo (ex. un logiciel de gestion complète d’une entité universitaire comme l’IFRI), où chaque groupe développe un module selon une méthodologie assignée, avec collaboration inter-groupes et tout le travail sur GitHub (branches main/dev/dev-moduleX, pull requests + revue + merge, et issues). L’évaluation combine alors une note globale et une note spécifique au module. L’enseignant indique en début d’année la formule retenue.

Conseils et bonnes pratiques

  1. Commencez tôt et travaillez régulièrement, en équipe.

  2. Gardez le client (l’enseignant) dans la boucle aux moments prévus par votre méthode.

  3. Documentez au fur et à mesure : n’attendez pas la fin.

  4. Tout sur GitHub (branches, PR, revues, issues) ; commits réguliers.

  5. Testez avant de livrer ; soignez le README et la vidéo.

Note

Les dates de rendu et la composition des groupes sont communiquées par l’enseignant en cours.
